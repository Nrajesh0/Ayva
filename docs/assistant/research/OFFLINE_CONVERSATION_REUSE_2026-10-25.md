# Offline conversation reuse for Run — 25 October 2026

## Finding

There are reusable parts, but no verified open-source package in this review supplies a broad, context-aware, ChatGPT-like conversation assistant for Android without trained models and without authored content. The strongest approach is one conversation interpreter (or a small native dialogue DSL), explicit state/reference handling, typed language utilities, and curated content retrieval. Installing many competing chatbot engines would reproduce Run's routing conflicts.

I reviewed **45 actual repositories** through GitHub. A first-pass OpenDial URL and a separate UD dataset URL did not resolve and are not counted as projects; OpenDial was then checked at its actual repository. Evidence is recorded in the companion source manifest with exact inspected default-branch commits. I read project READMEs/licenses where available and inspected selected build files, implementation, dictionary notices, dataset subdirectory licenses and state/persistence documentation. This is static due diligence, not a compatibility certification, Android benchmark, or complete transitive-license audit. Recommendations below are engineering assessments; a recent commit is not proof of maintenance quality, and an old commit is not proof of failure.

Run context inspected: native Kotlin/Android application, minimum SDK 24, Kotlin 2.0.21, Room 2.6.1, existing encrypted assistant/session state and native task/habit action executors. Existing conversation routing spans several handlers and stores pending questions and planning state. Reuse must improve this system rather than introduce a second source of truth.

“No models” here excludes pretrained LLMs, embeddings and trained statistical NLP/classification components, even when they run offline. Authored rules, dictionaries, frequency tables, state machines, grammars, lexical search and symbolic constraint solvers can qualify. A library's API class named “Model” does not necessarily mean trained ML. Offline and model-free are separate checks.

## Recommended shortlist

| Need | First candidates | Why / boundary |
|---|---|---|
| More small-talk coverage and personality | Curated ChatterBot corpus + constrained Tracery-style generation | Closest to reusing content rather than writing every reply. Still requires editorial/context rules; no ChatterBot training is needed. |
| An actual symbolic conversation engine | RiveScript Java as a low-complexity baseline; ChatScript as the richer challenger | Choose at most one. RiveScript is easier to prototype, ChatScript has stronger concepts/rejoinders/facts. Neither supplies Run-specific conversations automatically. |
| Interrupted conversations, pending questions, returning to a topic | KStateMachine; Tinder StateMachine as the smaller alternative | Kotlin-first transition tools. Run already stores state: this improves structure, not automatic intelligence or memory understanding. |
| Composable edits rather than competing regexes | better-parse; ANTLR only if grammar complexity warrants it | Produces typed operations from authored grammar. Actual pronoun/entity resolution remains a separate Run component. |
| Dates, time, quantities and units | Recognizers-Text Java evaluation; Natty secondary; Chrono as a reference/optional JS challenger | Preserve named date roles and ambiguity metadata. .NET examples do not establish Java feature parity. |
| Typos | Reviewed Java SymSpell port | Correct command vocabulary conservatively; retain original names/values. |
| Broader topic associations | Small attributed ConceptNet subset | Associations may guide a follow-up, not prove a fact or silently add an item. |
| More capable structured scheduling | Choco-solver later | It solves already-structured constraints, not conversation; native Android feasibility is unproved. |
| Better real conversation scenarios | Taskmaster, Schema-Guided Dialogue, selected MultiWOZ examples | Reference and adapted scenario material, not a runtime language model or executable knowledge base. |

Do not install every item above. Initially compare the current system, a minimal RiveScript branch, and an English-only ChatScript branch on the same inputs. If the engine adds little beyond the state/grammar/content improvements, keep the simpler native runtime. Do not require a large native rewrite merely to add a conversation library.

## Engines: deeper assessment

### ChatScript

Its concept sets can match families of related words rather than literal strings, rejoinders can follow the previous turn, and variables/fact triples can preserve a structured conversation context. Its native English POS processing is documented as rule-driven in `LIVEDATA/ENGLISH/POS`, followed by a garden-path parsing pass. The README explicitly lists Android; `SRC/common.h` includes an Android branch and documents `NOMAIN`/`InitSystem` for embedding. This is stronger evidence than generic C++ portability, but no current Android JNI integration was built in this review.

The real costs are a native build, Android filesystem/asset handling, engine lifecycle and concurrency, authoring/debugging its language, and bridging Run's persisted state. Its dictionary knowledge is not a broad factual conversation pack. The root engine is MIT, but `DICT/License readme.txt` has separate commercial-use conditions for foreign TreeTagger dictionaries/integration. English WordNet materials also carry their own notices. Build an English-only restricted package first; do not ship every bundled asset or enable process/network/database functions unnecessarily.

Verdict: strongest richer symbolic engine to **prototype**, not an unconditional replacement recommendation.

### RiveScript Java

The inspected code exposes user history and variables; the language supports triggers, conditions, context-dependent follow-ups and topic selection. It would let us maintain personality and domain dialogue in data files rather than adding Kotlin branches for each wording. MIT and Java are favorable. However, the inspected default-branch commit is from 2019; repository `pushed_at` is not proof that its core is being actively developed. The build still needs Android/R8, dependency and state-storage checks.

It is still an authored pattern interpreter. A wildcard does not understand that “remove that” refers to a particular checklist item. Run must supply the focus/pending object and validate the resulting typed operation. Avoid arbitrary object macros or script callbacks that bypass the existing action executor.

Verdict: best inexpensive **conversation-engine baseline**; it may be sufficient after state/content work, but does not settle the question without a comparison.

### AIML, Rosie and Program Y

These separate three things people often conflate: AIML is a dialogue format, Program Y is an interpreter/platform, and Rosie is a content collection. Rosie is the closest of the original suggestions to a ready small-talk pack, but it is GPL-3.0 and Pandorabots-oriented. Program Y has MIT-style interpreter text, while GitHub does not resolve its license cleanly, and it carries a large Python dependency/integration surface. Neither fact grants blanket permission for all bundled bot content.

Verdict: useful historical/content references; weaker direct candidates for proprietary native Android Run than they first appear.

### Emora STDM and OpenDial

Emora's state-transition/Natex design is particularly relevant to short follow-ups, guarded transitions and mixed-initiative dialogue. Its source package declares MIT, but I did not retrieve a root license grant. It uses Python and NLTK macros; an import must resolve licensing and resource/model usage rather than assume everything is pure rules.

OpenDial uses probabilistic rules and Bayesian dialogue state, with optional parameter learning and speech integrations. That is a valuable research architecture, but a manually specified probabilistic domain is still different from a trained language model. Under Run's strict requirement, its enabled configuration would need explicit review. No root distribution license was verified here.

Verdict: study the designs; do not make either a production dependency based on this review.

## Projects that sound suitable but need qualification

- **Duckling:** source tree includes generated ranking classifiers, including `Duckling/Ranking/Classifiers/EN_XX.hs`; it is not sufficient to call the whole default system “rules only.” Its test corpus and extraction rules are still useful references.
- **Wink NLP, OpenNLP, CoreNLP:** offline model loading remains model loading. Evaluate isolated deterministic utilities, not the entire trained NLP pipeline.
- **NLP.js / Rasa:** some rule components exist, but their usual intent/NLU paths involve training and their deployment shape does not suit native Android without significant work.
- **ChatterBot:** do not confuse the learning engine with the separate plain-text corpus. We can adapt corpus dialogue into authored rules without deploying the engine or training anything.
- **Botpress / Botkit:** platform/channel tooling and current LLM-oriented workflows do not give Run an embedded no-model conversation brain. Botkit is archived; current versus historical Botpress code/licenses must not be mixed.
- **Lucene:** current mainline build instructions require JDK 25. It is not an automatic Android dependency. A Room FTS4 index of reviewed text is a more proportionate first retrieval experiment, without assuming FTS5 on all Android devices.
- **Choco / Timefold:** a constraint-programming “model” is authored math, not necessarily trained ML. They can fit the no-trained-model principle, but JVM requirements/footprint and timeouts still matter; Timefold's current Java 21+ baseline is a major Android integration question.

## Where reuse would change Run

| Existing area | Reuse / design change | Observable user benefit |
|---|---|---|
| `ConversationRouting.kt` and `OfflineAssistant.kt` | One top-level ownership decision and one structured dialogue event; explicit Chat/Plan/Talk semantics remain authoritative | A summary question cannot be swallowed as an added topic; pending answers do not become unrelated tasks. |
| `AssistantSession.kt`, `PlanningDialogue.kt` | Typed topic frames plus guarded transitions/history (with or without a state library) | Interrupt for a question, then resume the exact pending exam/item date. Remember who/what “it” refers to. |
| `ConversationMeaning.kt`, `PlanLanguage.kt`, trip interpreter | Grammar/typed entity extraction followed by context resolution | Understand a broader set of corrections and compound edits without duplicated handler competition. |
| `GeneralConversation.kt` and knowledge handler | Authored topic rules, curated corpus, lexical retrieval, constrained response grammar | Broader small talk, less repetition, consistent Run personality and relevant follow-up questions. |
| Existing native executors and plan store | Keep them as the write boundary; libraries return proposed typed changes | Conversation cannot write a guessed date or “successful” action that never reached the actual task/habit record. |
| Existing scheduling logic | Optional bounded symbolic solver after parsing, if justified | Detect unavailable resources, dependency violations and feasible alternative schedules. |

The hard part is not only routing. A useful frame should distinguish tentative suggestions from commitments, pending answer type, main goal and subtasks, named date roles, last referenced item, negation/correction, unresolved ambiguity and confirmed saved state. Libraries do not infer this state correctly merely because they store variables. Run already implements pieces of it; consolidate and extend rather than duplicating them.

## Content, memory and personality

The best dictionary-like reuse candidate found is a **reviewed subset of `chatterbot-corpus`**, not an entire third-party personality. Its English greeting/conversation YAML files are inspectable and its root license is permissive, but user-contributed content needs file-level provenance/editorial review. Extract examples and topic coverage, then author concise Run-specific responses and explicit conditions. Remove invented personal experiences, unsourced factual answers, irrelevant jokes and fixed reply chains that lose context.

Use a grammar such as Tracery for surface realization only after a response act is chosen: acknowledge, ask one missing detail, explain a supported concept, compare a stated option, summarize, or close. Track recently used reply families and select contextually; random synonyms alone do not improve reasoning. The same response family must not replay after every user turn.

For lexical retrieval, store reviewed answer blocks with topic IDs, source/attribution, variant questions, freshness notes and allowed follow-ups. A keyword or FTS hit is not evidence that the answer applies; require a topic/intent match and decline unrelated retrieval. Existing Wordset/WordNet synonyms can help normalize concepts but are not broad world knowledge. A small ConceptNet subset is optional, and its data attribution/share-alike conditions are separate from code licensing.

Taskmaster, SGD and MultiWOZ are useful for discovering actual turn structures: a date in the opening message, changing only one slot, declining a suggestion, switching domain, and returning to a question. They can support manual design and an eventual acceptance corpus without training a model. They are not production-ready response content; booking dialogues must not cause offline Run to pretend it booked a hotel or flight.

## Implementation recommendation and acceptance boundary

1. **Consolidate state and interpretation first.** Compare native typed state with KStateMachine, and prototype a small better-parse grammar for corrections and queries. This does not require replacing the current planner or encrypted session store.
2. **Compare conversation engines, do not adopt both.** Give RiveScript Java and a restricted English ChatScript the same small Run-authored dialogue packs. The baseline remains the current native implementation; importing a runtime must show a concrete improvement over it.
3. **Expand curated content and realization.** Review ChatterBot corpus material, define Run's stable persona, and add topic-conditioned response variation. Use templates/grammars without inventing state or personal history.
4. **Unify entity extraction and date policy.** Evaluate Java Recognizers/Natty against current parsing; use Chrono/Taskmaster examples as references. Keep partial dates, certainty, source spans and named date roles separate from timestamps.
5. **Add knowledge retrieval and richer scheduling only where demonstrated necessary.** Curated Room FTS and optional graph subsets precede large search/solver runtimes.

A future implementation evaluation should use a small necessary set of complete conversations, not a large phrase-by-phrase test factory. Include: hello without an agenda dump; an ordinary multi-turn topic with a short follow-up; “why?” after a suggestion; a trip/exam date in the first line; changing the return date without changing travel; “maybe” versus “add”; remove/undo/summary; a task date capture in Chat versus discussion in Talk; habit pause/resume; typo tolerance without changing names; and interruption/resumption after a restart. Log the selected interpretation and frame updates to diagnose failures. Measure APK impact, cold start, bounded per-turn latency, memory and ability to persist history on an actual supported Android device. No such measurements were produced in this research.

No numerical capability score or forecast of “ChatGPT equivalence” is justified by reading repositories. Expect broader supported conversations, better follow-up continuity and less repetitive responses; do not promise arbitrary reasoning, current facts or fluent handling of every paraphrase without a model.
